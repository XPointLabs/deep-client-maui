# Client Performance Audit

| Priority | Area | Evidence | Impact | Fix |
| --- | --- | --- | --- | --- |
| P0 | Chat message bindings | `ChatMessageItem` and `GroupChatMessageItem` recalculated attachment type, image sizing, labels and reaction chips on every MAUI binding pass. | Scrolling and opening media-heavy chats paid repeated LINQ/string work for every visible cell. | Cache attachment presentation and reaction chips when the message item is created; keep only playback and preview path mutable. |
| P0 | Incoming message refresh | One-to-one and group receive paths reloaded the whole recent-message page after any new envelope. | A single received message could rebuild 100 message rows, reset image preview scans and move scroll state. | Upsert only the received/reaction-updated messages that belong to the active conversation and mark that conversation read. |
| P0 | Group chat first paint | Opening a group loaded local messages, then synchronously performed network group refresh before the page was revealed. | Group dialogs opened noticeably slower than one-to-one chats and slower than Telegram. | Open from local cache first; background auto-refresh continues after the page is interactive. |
| P1 | Collection updates | `ObservableRangeCollection.AddRange` emitted `Reset`, and older-message prepend inserted rows one by one. | MAUI `CollectionView` rebuilt visible layout instead of applying stable incremental changes. | Emit range `Add` notifications and use `InsertRange` for history pagination. |
| P1 | Chat reveal delay | Chat pages added a fixed 32 ms delay before revealing messages and then a second delayed scroll pass. | Every chat open included artificial latency even when data was ready. | Reveal immediately on the main thread and queue one scroll-to-end request. |
| P1 | Image preview loading | Every message add/reset rescanned all messages; preview work requested during an active load was dropped. | Image-heavy chats did extra list scans and sometimes waited for a later sync to show thumbnails. | Process only new collection items when possible, de-duplicate attachments in flight and rerun once if new work arrived. |
| P1 | Conversations first screen | `ConversationsPage.OnAppearing` waited for inbox network sync before first render/return. | Main list startup and back-navigation felt slower than Telegram, especially on weak transport. | Load cached conversations first, then run network sync in the background. |
| P2 | Initial chat page size | Chat open loaded 100 rows before the first usable render. | Large templates made first layout heavier than needed on Android. | Reduce the first page to 60 rows while keeping older-message pagination. |
| P2 | Call polling | Incoming call polling still ticks every second on the conversations page. | Low but constant wakeups while the page is open. | Keep as follow-up after replacing call signaling with push-driven wakeups. |
| P2 | Android transport listener wait | Local XRay listener probing uses blocking waits during tunnel startup. | Can add startup latency on older devices. | Keep as follow-up because it touches transport lifecycle and needs device VPN regression testing. |
